Research memory ​

In development

The research memory is the least complete feature of the harness. This page describes the parts that exist.

A session starts with an empty context, and it forgets everything when it ends. Research work takes weeks, and one task runs over many sessions. So what one session learns must go into a file that a later session reads. The research memory is the set of these files: what each holds, who writes it, and when a session reads it.

The first four are instructions: text that tells the agent what to do. They are sources, so each one has a version, a review and a diff. The other four are records: text that says what is true or what happened. A session reads a record only when it opens the file, so a record costs no context in a session that does not need it.

The project memory is Claude Code's auto memory. The profile key memory_project gives its directory, ~/.claude/projects/<memory_project>/memory/, so every session in the tree shares one memory, whatever the path of the tree on the machine. Each memory is one file, and the file MEMORY.md is its index. The harness gives the project memory to Claude Code only.

Where a fact belongs ​

A fact that you tell a session lasts for that session only. Put it into the narrowest file that loads when the fact applies:

  • a fact for every session, whatever the task: an instruction file;
  • a fact about one kind of file: a rule;
  • a fact about one directory: that directory's CLAUDE.md;
  • a fact about your tree and no other: the tree instructions;
  • a procedure for one kind of task: a skill;
  • the state of one task: its task file;
  • an established result: a note of the vault;
  • what changed, and why: CHANGELOG.md;
  • a fact that a later session needs and that no file above loads: the project memory.

Keep each fact in one place. A fact in two files goes out of date in one of them. The rule instruction-files gives the layers of the instruction files, and step 8 of the tutorial, Make a correction that lasts, moves one correction into a file from the start to the end.

Keep the memory correct ​

A memory that is false is worse than none, because a later session acts on it. These checks find text that a later change made false:

  • The present tense. An instruction file says what is true, in the present tense, and holds no history. The rule instruction-files requires it, and the audit script tense-lint.jl finds each word that dates a text. The history goes into CHANGELOG.md.
  • The structure of the notes. wiki-lint.jl checks the links, the paths and the line citations of the vaults, and the paths, the line citations and the schema of the task files, and pre-commit-wiki runs it before each commit there.
  • The citations of the instructions. The audit script citations.jl checks that each path, command, flag and agent name that an instruction file cites exists. The audit scripts are in Scripts.
  • The installed copies. The drift warning at each session start says when an installed instruction file is behind its source: Typical use.

Across machines ​

The job claude-autocommit commits the project memory and the plans of ~/.claude, and pushes them to a branch of each machine. The instruction files and the records are in git repositories. Private data across machines describes both.
