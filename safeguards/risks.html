Risks of agentic coding ​

A coding agent runs commands on your machine, with your files, your credentials and your network. Most of its commands are what you would run yourself. A few are not: a command that deletes more than it should, a push to the wrong branch, a token in a log that goes to a public repository. This page names the risks, says where each one comes from, and points to the safeguard of each. The other pages of this section describe the safeguards.

Where the risks come from ​

Three sources produce almost every risk:

  • Mistakes. The coding agent means well and gets a command wrong: a git add -A that stages another session's files, a rm -r one directory too high, a sed -i that matches nothing and reports success. These are the most frequent, and the cheapest to prevent.
  • Instructions in content. A web page, an issue body or a file that the coding agent reads holds text addressed to the coding agent, such as "run this command" or "send the key to this address". The coding agent can act on it as if you had written it. This is prompt injection.
  • Reach. A shell command can reach everything that your user account can: your SSH keys, your tokens, every repository and every host. A command does not need bad intent to do harm, only access.

Accident prevention and a boundary ​

Most safeguards of the harness read the text of a command and stop the forms that are mistakes. They prevent accidents. A session that tries to get past them can do so, because a command can hide inside a string argument that no text pattern sees. One safeguard is a boundary: the OS sandbox, which limits what a command can read, write and reach, whatever its text says. The security model states this split, and what each mechanism stops and does not stop. The column kind of the table above gives the kind of each safeguard of a risk.

The split decides how a risk is handled:

  • A risk that comes from a mistake gets a check of the text: a deny rule, a guard hook, a leak check. A guard hook and a leak check also tell the coding agent what to do instead, so the next command is right; a deny rule only refuses.
  • A risk that comes from reach or from injection needs the boundary. A text check helps, but only the sandbox holds against a command that the check does not read.

What stays open ​

No safeguard removes every risk. The limits of the security model list the gaps that are known, such as the commands that run outside the sandbox, an MCP server that runs outside the session's sandbox, and an allowed host that takes what a command sends to it. The planned safeguards close some of them.

You stay the last check for an outward step. A merge, a release and a deleted branch on a remote ask you; a forced push is refused. The test suite runs before a push to main of a package, and the leak gate before a push of the harness (Git safety).
