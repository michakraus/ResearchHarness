The harness command ​

harness is the one command of the harness. The harness command describes its subcommands and their contract for a user: a subcommand that changes something prints its plan, and --apply makes the change. This page describes the code: which module implements which subcommand, and which modules have only test cases.

The entry point is bin/harness. The code is the Python package lib/harness/, which uses the standard library only. Each module that owns a subcommand has a function register, which adds its subcommand to the argument parser. Most modules also have a function selftest, which runs their own test cases. harness test runs every selftest, the groups of the hook probe hooks/probe.py and the contract sweep, each as a part in a process of its own. Three subcommands live in the adapters: settings and trust in adapters/claude/adapter.py, and permissions in adapters/opencode/adapter.py. The adapters describes them.

harness ​

The executable script bin/harness, the entry point of the harness. Put bin/ on the PATH, then run harness --help for the list of subcommands, or harness <subcommand> --help for one subcommand.

The script first checks the version of Python. It needs Python 3.14 or later, the one version that the harness is tested on. An older interpreter prints the version that it found and the version that it needs, and the script exits with status 2. The script uses no syntax newer than Python 3.0, so an old interpreter reads it without a syntax error.

Then the script chooses the interpreter of the command. The Python environment of the harness is at $RESEARCH_HARNESS_PYTHON, an absolute path, or else at ~/.local/share/research-harness/python/; it is working when its bin/python exists and starts.

  • With a working environment, the command runs on its bin/python. On another interpreter, the script starts itself there with the same arguments, in the same process.
  • In a session, where SANDBOX_RUNTIME or CLAUDECODE is set, with no working environment, the command runs on the interpreter that started it, after one line on stderr that names the environment and harness install --apply. A session never starts uv.
  • Otherwise the script finds uv on the PATH or in ~/.local/bin. On Linux without one, it fetches the uv release that it pins into ~/.local/bin and checks the sha256 of the archive; the download follows one redirect, to release-assets.githubusercontent.com, and no other. Then it runs uv sync --locked --no-dev into the environment, writes the environment's stamp, the sha256 of uv.lock and the group, and starts itself on the new interpreter. The environment is made on Python 3.14 (UV_PYTHON overrides it), and uv downloads a managed 3.14 where none is installed. A sync that fails, or that leaves no working environment, removes the environment when the sync made it; a uv that the fetch wrote and checked stays in ~/.local/bin.

The chosen interpreter goes into RESEARCH_HARNESS_INTERPRETER, which each child process inherits. A process that finds it set does no lookup: it runs when it runs on that interpreter, and otherwise starts itself there once; a process that such a restart started and that still runs elsewhere exits with status 2, so the restart never loops. Two paths name one interpreter when their real paths and the directories of their environments, where a pyvenv.cfg lies, are equal. Each refusal is one line on stderr and exit status 2: no uv on macOS or on a system other than Linux, a relative $RESEARCH_HARNESS_PYTHON, a sync that fails or that leaves no working environment, and on Linux a download that fails, a checksum that is not the pinned one, an archive with no uv, an architecture other than x86_64 and aarch64, and a redirect to another host.

Last, the script adds lib/ to the module path and calls main of cli.py. It follows a symbolic link to find lib/, so a link to the script in another directory also works. install.py loads the script as a module, boot, for the environment's path, its stamp and the sync; only a run as a script starts the command.

__init__.py ​

The package file of lib/harness/. Its docstring is the contract of every subcommand, and harness --help prints it: a subcommand that changes something does a dry run by default, exits with status 1 when something would change and 0 when nothing would, and --apply makes the change. Exit status 2 is a usage error or a failure.

It defines what the other modules share:

  • REPO, the path of the checkout;
  • HarnessError, a failure that the subcommand reports in one line, after which harness exits with status 2;
  • changing(parser), which gives a subcommand its --apply flag;
  • outcome(args, changes), the exit status of a subcommand that changes something: 0 after --apply or with no change, otherwise 1.

A new subcommand that changes something uses changing and outcome, so that it keeps the contract.

cli.py ​

The argument parser of harness. main loads the adapters through frontends.py first. When an adapter fails to load, harness exits with status 2 before any subcommand runs. Then main adds the global options --profile F and --models F, each subcommand of the modules and the adapters, and harness test from testrun.py. On a HarnessError of a subcommand, harness prints one line, harness <subcommand>: <message>, and exits with status 2.

testrun.py ​

The subcommand harness test. parts gives the table of the parts, by name: each module and adapter with a selftest, the groups of doctor.py (its GROUPS) and of hooks/probe.py (PROBE_GROUPS, which a case checks against the probe's GROUPS), and the sweep. A part runs in a child process: a probe group as hooks/probe.py <group>, every other part as harness test --part <name>, an option that --help does not show. The child prints one line per case and, last, <n> cases, <w> wrong.

run_parts runs the parts in a pool of --jobs threads, each of which waits on one child, and report prints each part's output whole, in the order of the part names. A child that prints no summary line, or whose exit status does not agree with it, counts as one more failed case, with its stderr; a crash so shows its traceback. A child that runs longer than 300 s is stopped with its process group and counts as one failed case. An error, an interrupt, a SIGTERM or a SIGHUP of the run stops the children that still run.

changed reads git diff --name-status BASE...HEAD, both paths of a rename or a copy, and owners maps each path to its parts by the table OWNERS. take_slot holds one of the two slot files with an exclusive flock. Development describes the selection, the options and the slots for a user.

frontends.py ​

The list of the frontends, claude, opencode, omp and antigravity, and the loader of their adapters. load imports each adapters/<frontend>/adapter.py by its path, in that order, once.

Each adapter must define six members: NAME, TEMPLATES, register, plan, selftest and RESTART. When an adapter fails to import, harness exits with status 2 and prints its path, its line and the last line of the exception. When an adapter lacks a member, harness exits with status 2 and prints its path. No adapter is skipped.

The module also defines Plan, the part of harness install that one frontend returns: the files to install, the warnings, the installed files with no source, the refused files with their messages, and the steps that run after the files. A later frontend reads the plan of an earlier one; oh-my-pi reads the rules of the Claude Code plan.

The adapters are described in the adapters.

install.py ​

The subcommand harness install [--apply] [--force]. It reads the profile and the model tables, and asks each adapter for its plan, in the order of frontends.py. A plan writes nothing, so on a refusal the subcommand exits with status 2 before any file is written.

Before it writes, the subcommand checks every target of the Julia environment and of each plan (check_files). The subcommand exits with status 2 at once if a target is a symbolic link, a directory or a file that cannot be read, or if a directory above a target is a symbolic link or a file. Under --apply, it also exits with status 2 before anything is written if the install changes a target that it cannot write, or whose mode it cannot change. A dry run prints its whole plan and count line first, then that refusal, and exits with status 2.

Then the subcommand installs the Julia environment of the scripts: it copies Project.toml to ~/.local/share/research-harness/julia/, or to $RESEARCH_HARNESS_JULIA, and instantiates it. Then it plans the Python environment of the harness as one line, python environment (install_python_env): a change when its interpreter does not start or when its stamp names another uv.lock or group. Under --apply it runs uv sync --locked into it, with the dev group when the profile sets develop = true and with --no-dev otherwise; a sync that fails exits with status 2 and its last stderr line. Then it installs the files of each plan, prints the warnings, and runs the steps after the files. The subcommand adds one warning of its own: behind_origin warns when the checkout is behind its local origin/main. It fetches nothing. It prints the count line, and after --apply the restart line of each frontend whose files changed. A file that differs in its bytes or its mode is a change. --force replaces a file that an adapter refuses to replace.

The module also holds the helpers of a layer that copies its sources one to one: source_files, check_targets and stamp_bytes, the stamp that the SessionStart hook hooks/install-drift.py computes again.

Its cases check that the install exits with status 2 and names the file on a broken profile or models.toml, and that it exits with status 2 and writes nothing when an adapter fails to load. They also run the restart cases of install_cases.py, and behind_origin on a scratch repository whose origin/main is ahead of, level with and behind its HEAD.

install_cases.py ​

The helpers for the test cases that run harness install end to end. It has no subcommand and no selftest of its own.

Scratch creates a scratch HOME below a temporary directory: ~/.claude/skills/, an OpenCode directory, a Julia directory with a copy of Project.toml, a Python environment that the install plans as synced (python_env), the tree instructions, and the dummy profile with tree_agents set. Scratch.run runs harness install in a process of its own, with HOME, OPENCODE_CONFIG_DIR, RESEARCH_HARNESS_JULIA, RESEARCH_HARNESS_PYTHON and PI_CODING_AGENT_DIR in the scratch directory. A run that takes more than 60 s is a timeout.

restart_cases checks the restart lines of harness install. Each case changes the files of one frontend, or of no frontend, and checks that only the restart lines of the frontends that changed follow the count line. install.py calls it, and the adapters use Scratch in their own cases.

profile.py ​

The private profile and the rendered output of a template. It gives three subcommands:

harness render TEMPLATE
harness get KEY
harness leaks [--commits F]

render prints a template with each placeholder {key} replaced by its profile value. A list value repeats the line, or the JSON list element, once for each item. A table value renders only on a line that holds the placeholder alone, as the members of a JSON object. On a placeholder that the profile does not have, the subcommand exits with status 2. Every subcommand reads a value of autocommit_branch. If the key is missing, the default is main on the template host, or on every machine when template_host is not set, and memory/<short host name> on every other machine. The template host is the machine whose Claude Code memory is the template for the other machines; the profile key template_host names it by its short host name. get prints one value, one line for each item of a list; on a key that the profile does not have, it exits with status 2. render of the settings template also adds its network rules (network.py). Each subcommand loads the profile into a frozen dataclass, Profile, and exits with status 2 on an unknown key, a missing required key, a value of the wrong type or a retired key, with one line that names the file and the key.

leaks searches every tracked file and its path for each of the private strings (the profile's leak list), and for the name of each directory below a repository_roots entry and each org entry. The repository's own owner/name and the host of its GitHub Pages site, owner.github.io, do not count as a hit. It also renders each template with examples/profile.toml and searches the result. With --commits F it also searches the paths, the added lines and the message of each commit that F names. The pre-push hook calls it in this way. The subcommand exits with status 1 on a hit.

The module also reads the model tables for the adapters, into frozen dataclasses. On a table that names a model tier by an old name, a table that no frontend reads, a key that a table does not name or a value of the wrong type, the subcommand exits with status 2. Adapting the profile describes the keys.

githooks.py ​

Three subcommands that copy shared files into the repositories of the research tree. The research root is $RESEARCH_ROOT, or ~/Research if it is not set.

harness githooks [--apply]
harness wiki-lint-hook [--apply]
harness workflows [--apply]

githooks copies githooks/pre-commit, githooks/pre-commit.jl, githooks/pre-push, githooks/pre-push.jl and scripts/test-layout.jl into .githooks/ of each git repository directly below Packages/ and Experiments/, and sets core.hooksPath. wiki-lint-hook copies githooks/pre-commit-wiki as the pre-commit hook of the prose repositories that WIKI_REPOSITORIES names. workflows copies the canonical files of githooks/workflows/ and deletes the retired CompatHelper.yml.

A session cannot write .git/config. So a run that cannot set core.hooksPath prints the command for each repository, and exits with status 2. The module also gives research_root, repositories and git to other modules. It has no selftest; the sweep runs its dry runs and its --apply. Git hooks and workflows describes the copied files.

repos.py ​

The subcommands harness clone [SELECTION ...] [--apply] and harness repos status|pull|push|sync [SELECTION ...]. They read the repository table, repositories.toml beside the profile or $RESEARCH_HARNESS_REPOSITORIES. A top-level key names a fixed repository (knowledge, environment, tasks, library), and a table names a group (packages, experiments, papers, books, talks, projects); each directory is the key in title case below the research root. load_table refuses an unknown key and a directory name that has a / or starts with .. Without a table, repos takes each git repository that it finds, and clone stops.

clone refuses the whole run when a directory is in the way, before the first clone. status, pull, push and sync fetch in parallel, eight at a time, and status asks gh or glab for the open pull requests, also in parallel. pull merges --ff-only, and skips a branch whose incoming commits change a file with local changes. push pushes one repository at a time and skips a branch that is also behind, and a branch that is not the default branch unless --include-topic-branches. The dry run names the .jl files of each push. --no-verify (or --skip-hooks) skips the pre-push suite; use it only for a push with no Julia source and no [compat] change. After a push, the subcommand compares the local commit with the remote branch, as git ls-remote reports it.

Run push and sync in your own terminal. The pre-push hook of each repository can run a full test suite, so the subcommand can take hours, and a tool call of a session stops after ten minutes. The selftest runs each subcommand on scratch remotes below a temporary directory, and the query for pull requests on a stub of gh and glab; the sweep runs the dry runs.

update.py ​

The subcommand harness update [--apply]. It works on the checkout that runs it, when its branch is main with the upstream origin/main. It fetches, prints the new commits and their files, and exits 1 when there is one. --apply needs a terminal: it shows the whole diff, asks y/N, merges --ff-only and runs harness install --apply in a process of its own, from the merged checkout. It stops at a detached HEAD, a pinned checkout, at changes to tracked files, and at commits that origin/main lacks. The selftest runs it on a scratch remote and its clone.

dotfiles_kit.py ​

The subcommand harness dotfiles-kit [--apply] DEST. It reads examples/dotfiles/kit.toml, which names each file of the dotfiles kit and its class, and compares the chezmoi source DEST with the kit. A code file that is missing, or that differs in its bytes or in its execute bit, is a change. A seed file is a change only when it is missing. --apply copies each change, and replaces a symbolic link at a code file's path rather than write through it. The subcommand refuses a DEST that is not a directory, and the applied source ~/.local/share/chezmoi or a directory below it; it compares the resolved DEST and each of its parents with the applied source by device and inode, so a case variant or a firmlink of the applied source is refused too. Before it compares the first file, it checks that the directory of each file of kit.toml resolves inside the resolved DEST, and exits 2 on one that resolves outside it, or that does not resolve because of a loop of symbolic links. A code file that cannot be read exits 2, and --apply exits 2 on anything at a code file's path that is not a regular file or a link, such as a directory or a FIFO. The dotfiles command describes the kit and the scripts that it installs.

The selftest runs it on a scratch kit with its own kit.toml: the dry run's list, --apply and the dry run after it, a seed file that exists, each refusal of DEST, each directory that links out of DEST, and each malformed kit.toml. Then it runs the command on an empty directory and checks that the list holds every file of the harness's kit.toml. The sweep runs the dry run on an empty fixture directory.

protection.py ​

The subcommand harness ci-protection [--remove-classic] [--apply]. It protects the default branch of each repository with a GitHub ruleset named main: no deletion, no force push, and the required status checks of the canonical CI.yml. It also turns on auto-merge and the deletion of merged branches. --remove-classic deletes the classic branch protection, but only where the ruleset passes every check.

The subcommand first runs githooks/verify-workflows.jl, and refuses when the workflows are not canonical, because the list of required checks depends on them. It calls gh api for each repository, and skips a repository that is private or where the user is not an admin. Run it in your own terminal: in a sandboxed session, only the first gh call of a process succeeds.

Its cases check ruleset_problem against the ruleset as GitHub returns it, and against one break of each check. The sweep does not run this subcommand, because it needs gh with a login.

fmt.py ​

The subcommand harness format [--apply]. It runs githooks/format-tree.jl, which runs JuliaFormatter over each tracked .jl file of the tree.

JuliaFormatter can stop the whole Julia process on some files. format-tree.jl records the file that it is about to format in a marker. When the process stops, the subcommand moves that file into a skip list and runs the script again, at most 40 times. At the end it prints the files that JuliaFormatter cannot handle. The marker, the skip list and the log go to $FMT_OUT, or to $TMPDIR if it is not set.

The dry run counts the files that the script would format, from its summary line. The module has no selftest, and the sweep does not run it, because it runs Julia over the tree.

changelog.py ​

The subcommand harness changelog [--apply | --check BASE], the changelog fragments of the harness checkout. Each branch writes its entry into a file of changelog.d/, so two pull requests never change the same lines of CHANGELOG.md. fragments lists the fragments, every changelog.d/*.md but README.md, and the dry run and --apply read that list. The dry run prints the ## Unreleased block that they make, newest first by the committer date of the commit that added each; --apply writes the block at the top of the ## Unreleased section of CHANGELOG.md and deletes the fragments. --check BASE reads git diff --name-status -z BASE...HEAD; unrecorded, a function of the changed paths and their status alone, names the first path below a code directory when no added path is a fragment. CI runs --check on each pull request.

Its cases check the join, the insertion into CHANGELOG.md, the order and the path classification without git, and the dry run, --apply and --check on scratch repositories with fixed commit dates. The sweep does not run it, because it reads the harness checkout and its history, not the fixture.

mutate.py ​

The subcommand harness mutate SPEC, the named mutants of the Python code. load reads the TOML spec, one table per mutant with file, anchor, old, new and tests. copy copies the tracked files of the checkout and its untracked files that git does not ignore into a temporary directory and makes it a git repository, because the parts docs and sweep read git ls-files. mutated replaces the one old after the anchor's line. Before any mutant runs, run refuses a spec that it cannot apply, a part that harness test --list of the copy does not name, and a copy that fails the spec's parts unmutated. each then applies each mutant alone, skips the test of a mutated file that ast.parse refuses, runs harness test of the copy with the mutant's parts, reverts the file, and prints the line that verdict gives.

Its cases check the spec, the anchor, the verdicts and the copy, and run whole runs and each refusal on a fixture git repository with a stub bin/harness; they never run the real suite. The sweep does not run it, because it needs a spec and runs harness test.

skill_triggers.py ​

The subcommand harness skill-triggers [--skill <name> …] [--apply --model <alias>], the test of whether each skill loads on the right queries.

It reads tests/skill-triggers/<skill>.toml for each skill of skills/. The dry run prints the number of queries per skill and the number of sessions that --apply starts. --apply runs each query as one claude -p session of 3 turns on the model that --model names, without the tools that write or run commands. A query loads a skill when the first Skill call of the first three assistant messages names it. A failed query runs twice more, and the majority counts. A skill passes when at least 8 of its 10 load queries load it and at most 1 of its 5 near queries does. The report goes to .scratch/skill-triggers/ below the research root. Every session costs tokens.

Its cases run the parser, the verdict, the majority and the pass rule, and run --apply on a fake claude. Typical use shows the commands.

doctor.py ​

The subcommand harness doctor [--full], the check that a machine's setup works. It is read-only, so it takes no --apply. It prints one line for each check: PASS, WARN, FAIL or SKIP, the name of the check and a detail, such as a version, a path or the reason. A FAIL line also names the section of the setup page that fixes it. The subcommand exits with status 1 when a check fails, otherwise with status 0; a WARN or a SKIP does not count. On a usage error, it exits with status 2.

It checks, in this order:

  • the machine: the system and the architecture. On Linux also the two kernel settings for user namespaces, the sandbox check bwrap --ro-bind / / --dev /dev --unshare-user --unshare-pid true, and socat.
  • the tools of Dependencies: each required tool is on the PATH, and each tool with a minimum on that page is at or above it; below it, or missing, is a FAIL. A missing tool that serves one frontend, one job or a push to the harness (the frontends, RTK, jq, juliaup, iTerm2 and gitleaks), or that only the sync of the Python environment needs (uv), is a WARN that says what stops without it. uv is looked for as the sync looks for it, on the PATH or in ~/.local/bin. When the version flag of a tool exits with a status other than 0, the check is a FAIL for a required tool and a WARN for an optional one. In a session's sandbox, which can refuse the flag, the check is a SKIP. When the flag exits with status 0 but the subcommand cannot read a version from its output, the check is a WARN with the tool's own text. The minimums are in MINIMUMS, and a case compares each with the page. The six Julia packages are read from the Manifest.toml of the Julia environment of the scripts. The Python environment of the harness is a FAIL when its interpreter does not start or is below the minimum of Python, a WARN when its stamp names another uv.lock or another group than the profile's develop, and otherwise a PASS. A lagging environment is also one change of the dry run of harness install, so the same run gives a FAIL on the install line, and doctor exits 1; harness install --apply fixes both.
  • the profile: it loads, the tree_agents directory and the OpenCode configuration directory exist, and the line autocommit_branch prints the value.
  • the install: the dry run of harness install reports 0 change(s), otherwise a FAIL with the count. Each warning of the dry run is a WARN line.
  • the jobs: Kaimon, ~/.julia/bin/kaimon; its server and the update job, with systemctl --user on Linux and launchctl list with the profile's launchd_prefix on macOS; lingering on Linux. When the autocommit job is enabled, ~/.claude must be the top of its own git repository, with an origin. The Kaimon token file must exist, with mode 600, and not be empty. Without Kaimon, its jobs and the token are SKIP, and so is the token without OpenCode, oh-my-pi and Antigravity, which read it. Antigravity counts as installed when ~/.gemini is a directory.
  • with --full, harness test and julia -e 'using Revise'. Without --full, both are SKIP.

The subcommand writes no file, starts no service and runs no --apply. It prints no secret: it reads only the existence, the mode and the size of the token file, and does not print the URL of the origin of ~/.claude. A session's sandbox refuses some of the commands, such as launchctl, and denies the read of the token file. There, these checks are SKIP with the reason, so run the subcommand in a plain terminal for its real verdict.

Its cases run each status of each check on a fixture: a scratch HOME and stub commands on the PATH that print what each tool prints on Linux and on macOS. They also check the exit status, the minimums against the page, that no token reaches the output, and one run of the subcommand on the fixture of the contract sweep, which changes no file. GROUPS splits them into five groups, minimum, linux, darwin, exit and process, and harness test runs each as the part doctor:<group>.

units.py ​

The cases of the systemd --user units in systemd/. The module has no subcommand. It renders each unit and its plist in launchagents/ with examples/profile.toml. Then it checks that both describe one job: the program and its arguments, the working directory, the environment and its PATH, the timer's triggers, the start at login, and Restart=always where the plist has KeepAlive. A section, a key or a repeated key that the check does not read is a problem. A continued line is a problem too. Every element of the PATH must be an absolute directory that the settings template keeps out of a session's writes, or a system directory. An empty element, which means the working directory, is a problem. The cases also apply a mutant to the rendered templates and expect a problem: for example a removed restart, an extra trigger or a session-writable directory on the PATH. Last, they check that render gives autocommit_branch its default when the profile has no such key: main, and memory/<short host name> on a host that is not the template host. Jobs and configuration describes the units.

script_cases.py ​

The cases of scripts in scripts/ that need no Julia. The module has no subcommand. It reads the critic's rsync copy from skills/build-part/evidence.md and copy_command from scripts/run-tests.jl, runs each on a fixture tree with a .env, a .env.ts, a .git and a .claude, and checks that the copy holds none of them. A control copy with no flag must hold the .env.ts. Then it runs scripts/spec-gate.py on a fixture task file and checks the verdict of each part: a part whose Files lie in two repositories is SPANS, unless its part tier is direct. It runs scripts/spec-validate.py on a fixture spec in the spec-delta format, with a control for each of a missing domain, a failing premise, a mutant with no row, a failing check on a head and a check that writes into the head; and it checks that spec-gate.py and spec-bundle.py take a part whose cell names spec.

network.py ​

The network rules of the Claude Code settings. The module has no subcommand. It reads settings/network.toml and the overlay network.toml beside the profile, and writes into the rendered settings template the WebFetch(domain:…) rules of permissions.allow and permissions.deny and the lists allowedDomains, deniedDomains and deniedDomainReasons of sandbox.network. A deny entry removes each allow and infrastructure host that it matches. install, render of the settings template and settings call it. The module exits with status 2 in two cases: a file breaks the schema, or the template holds a host of its own. Its cases check each rule, each of these exits, and that an overlay changes no file of OpenCode or oh-my-pi. The profile's loader refuses the retired profile key extra_domain. Adapting the profile describes the keys.

providers.py ​

The model providers of OpenCode and oh-my-pi. The module has no subcommand. It reads providers.toml beside the profile, which may be missing, and gives each frontend its entries: the provider object of opencode.jsonc and the providers of oh-my-pi's models.yml. The OpenCode and oh-my-pi adapters call it in install. The module exits with status 2 on a literal key, an unknown key or a value of the wrong type. Its cases check the mapping of each key, the merge of a frontend's own keys, and each of these exits. The profile's loader refuses the retired profile keys opencode_providers and omp_providers. Adapting the profile describes the keys.

sources.py ​

The names of the neutral sources: the five directories agents/, skills/, rules/, instructions/ and commands/, which belong to no single frontend. Each adapter reads them from here. The module has no subcommand and no cases.

curated_skills lists the curated skills below a directory: each subdirectory with a SKILL.md, except a hidden one and the directories of EXCLUDED_SKILLS. listing gives the agents of agents/ and the SKILL.md of each curated skill of skills/. code_list writes names as Markdown code in a sentence, for the text that the adapters generate.

frontmatter.py ​

The strict parser of the frontmatter of an agent or a skill, the block between the first two --- lines. It has no subcommand. Its cases run in harness test.

The parser accepts eleven keys, each once. A value is plain or in double quotes, and tools and skills take a block list. It refuses each other form, such as a flow list, a comment, an unknown key or a control character, with the file and the line, and harness exits with status 2.

parse_file also checks the neutral vocabulary. model must be a model tier: large, medium or small. Each tools item must be a neutral tool or mcp/kaimon/<tool>. The description of a skill has at most 1,024 characters and no < or >.

Its cases check each refused and each accepted form, and parse every agent of agents/ and every curated skill of skills/.

sweep.py ​

The contract sweep, the part sweep of harness test, which runs in every selection. It has no subcommand.

The sweep creates a fixture HOME in a temporary directory: the dummy profile and model tables, the files that the subcommands read, and a research root with one package and one prose repository. Then:

  • it runs the dry run of each subcommand and checks that it exits with status 0 or 1, prints no traceback and changes no file;
  • it removes each precondition alone, such as the profile or ~/.claude.json, and checks that each subcommand that needs it exits with status 2 and one line;
  • it runs --apply of githooks, wiki-lint-hook, workflows and trust, and checks that the dry run after it exits with status 0.

It does not run format, ci-protection, skill-triggers, doctor, test or mutate. Development describes the tests.

environment.py ​

The cases of the Python environment of the harness. The module has no subcommand. Its cases run bin/harness as a child process under a scratch HOME, with a fake uv that logs its arguments and makes the environment with python -m venv: a session with no environment, the marker, the first sync and a second run, the Python that uv is asked for, the restart with its arguments onto a working environment, in a session too, each refusal of the start, a failed sync that removes the environment that it made and keeps a directory that was there, and a restart that lands on another interpreter, which exits with status 2 instead of a loop. In the process of the cases, they check the marker that a start exports to its children. They also run the script, under a scratch HOME, on an interpreter that reports 3.13, and check that the script uses only a closed set of forms, each of which Python 3.0 reads.

The cases of the Linux download set the platform and the release URL through RESEARCH_HARNESS_TEST_PLATFORM and RESEARCH_HARNESS_TEST_UV_URL, which only they set, and serve fake archives from a local http.server: an unknown architecture, a download that fails, a checksum that is not the pinned one and a redirect to another host. No fake archive has the pinned sha256, so the download that succeeds, and the redirects, run in the process of the cases, with a patched checksum, and so does a start whose fetched uv makes no environment: the start refuses, and the uv stays in ~/.local/bin. Last, the cases run harness install on Scratch: the plan line, the sync with and without the dev group, an interpreter that does not start, a sync that fails, no uv, and a develop that is not true or false.

strict.py ​

The cases of the strict profile of the Python code. The module has no subcommand. Its first cases parse each .py file below hooks/ and each adapters/*/guard*.py with ast and fail on an import outside the standard library, in this repository and in scratch trees: hooks/probe.py may also import harness, and another file may not. The other cases run .githooks/pre-commit through git commit in scratch repositories, with stubs of ruff and basedpyright in a scratch Python environment and a second pair on the PATH: a clean commit, a staged file that each check refuses, a staged file that the formatter would change, which stays as it was in the work tree and the index, a violation that is not staged, and an environment without one tool or both. Development describes the profile.

docs.py ​

The check of the component pages of the documentation site, which runs in harness test. It has no subcommand.

The table KINDS maps each page of docs/src/components/ to the tracked files that are its components, and to the name of each. The check reads the level-2 headings of each page and the names in backticks in them. It fails when a component has no heading on its page. It also fails when a heading names something that is not a component of its page, so a removed component leaves no old section.

It also checks docs/src/dependencies.md: its three tables, and one level-3 heading below them for each tool of the tables, with no heading that names a tool outside them. So a new agent, skill, hook, script or tool needs its section in the same change.
