Git hooks and workflows ​

A git hook is a program that git runs at a fixed point, for example before a commit or before a push. When the hook exits with a status other than 0, git refuses the commit or the push. A GitHub Actions workflow is a file that tells GitHub which jobs to run on a push or a pull request.

The files of this page are in githooks/ and githooks/workflows/. Most of them are templates for the Julia repositories of the research tree; the others are scripts beside them. Two subcommands of the harness command install the templates into every repository below Packages/ and Experiments/ (see Clone, sync and trust):

  • harness githooks --apply copies pre-commit, pre-commit.jl, pre-push, pre-push.jl and scripts/test-layout.jl into .githooks/ of each repository, and sets core.hooksPath there.
  • harness workflows --apply copies the files of githooks/workflows/ into each repository that has a Project.toml. Dependents.yml and dependents.jl go only into the bases that the profile key dependents_bases names.

harness wiki-lint-hook --apply installs pre-commit-wiki into the prose repositories. Each copy is byte-identical to its template and is a tracked file in the repository. Edit the template, then install again; never edit a copy. The other scripts of this page run from the checkout. This repository has a pre-commit and a pre-push hook of its own, .githooks/pre-commit and .githooks/pre-push; they are not templates, and Development describes them. Both run basedpyright as CI does, on the interpreter of the harness's Python environment and with --baselinemode=lock, so a commit or a push that removes baselined errors must write .basedpyright/baseline.json again.

pre-commit, pre-commit.jl and pre-commit-test.jl ​

pre-commit is the shared pre-commit hook of the Julia repositories. It is a short bash launcher that starts pre-commit.jl beside it, in one Julia process. A commit with no staged .jl path, a deletion included, and no change below test/ passes without starting julia. Without julia on the PATH, any other commit is refused with pre-commit: julia is not on the PATH. The program runs these stages:

stagewhat it checkson a failure
0the violations of test-layout.jl, on a commit that touches test/blocks
1JuliaFormatter 2.14 or later, with the .JuliaFormatter.toml of the repositoryblocks
2fatou lint, with a limit of 60 swarns only
2.5each file is in Unicode NFCblocks
2.7the rules of ast-grep, with a limit of 60 sblocks on a line that the commit adds, warns on any other line
3using <package> loads, with a limit of 600 s, for a repository with a packageblocks

Stages 1 to 2.7 run on the staged .jl files only, a renamed file under its new name and a file that became a symlink too; a path with non-ASCII characters is read as it is, not in git's quoted form. A staged .jl path that is not a file, such as a symlink to a missing file or to a directory, is refused with one line that names it, before any stage runs. Stage 3 runs when a .jl file is staged, and also when only the deletion of one is: a deletion can break an include. Stage 1 checks each file on its own: a file that does not parse fails stage 1, with the first two lines of its error on stderr, the message and its location, followed by the parser's reason, and the other files are still checked. Stage 1 loads JuliaFormatter from the harness's Julia environment, which pins 2.14, and refuses an older release with one line that names its version, marking every staged file; JuliaFormatter 2.14 supports Julia 1.10 and later. Stage 1 has no time limit (K130 of KNOWN_ISSUES.md). Stage 0 reads .githooks/test-layout.jl, which harness githooks installs beside the hook; a missing copy blocks the commit. Every stage reads the working tree, not the index (K128), so a staged .jl file that also has changes that are not staged, one that git diff --name-only lists, refuses the commit before any stage runs: the hook prints one line per such file and asks you to stage the rest of the file or to move the unstaged edits aside. The listing runs with literal paths, with no external diff program or textconv driver, and without GIT_DIFF_OPTS, GIT_ICASE_PATHSPECS and GIT_GLOB_PATHSPECS. An unstaged change in a file that the commit does not stage refuses nothing. The lint only warns, because fatou lint reports false positives; without fatou on the PATH, or with a fatou that cannot start, the stage prints one line and is skipped. The staged paths reach fatou after --. A finding is a line of the form <path>:<line>:<col>: …; a non-zero exit of fatou with no such line is a failure of fatou, which the stage reports with its exit status and skips. The NFC stage does not change a file; run nfc.jl --apply to fix one. Stage 3 loads the package in a child process, in the environment of the repository, so that the versions of JuliaFormatter's dependencies in the hook's own process do not change what the package loads. A failed load shows at most 20 lines of its output, from the first line that holds ERROR:, or from its first line when no line does. A repository has a package when its Project.toml, read as TOML, has a name and a uuid; for a name with no uuid, the hook prints one line that no load test runs, which is no failure. A Project.toml that does not parse refuses the commit with one line that holds the first two lines of the error, the message and its location. A package name that Base.isidentifier refuses, or that the parser of the running Julia does not read as that one name, such as the keyword end, refuses the commit with one line, and no load test runs. The lint stage, the ast-grep stage and the load test run in a process group of their own: when the limit runs out, the hook sends the group SIGTERM, and SIGKILL 5 s later, waits at most 6 s after the SIGTERM on the monotonic clock, and does not wait for the output of a process that left the group. When you interrupt the hook, it kills that group on its way out. A commit with no staged .jl path and no change below test/ passes with no check. git commit --no-verify skips the hook.

Stage 2.7 runs ast-grep scan --custom-languages allow once over the staged .jl files, from the root of the repository. ast-grep uses the sgconfig.yml that it finds there or in a directory above it, such as ~/Research/sgconfig.yml, a copy of research-sgconfig.yml. A hit of severity error refuses the commit when a line of the hit is one that the commit adds: the stage prints ast-grep: FAILED and one line per hit, <file>:<line>: <rule-id>: <message>. A hit of severity error on lines that the commit does not add only warns, so the hits that a file already holds do not block an unrelated commit; a pure rename adds no line. The stage takes the added lines from the hunks of git diff --cached -U0 -M, with literal paths and with options that keep an external diff program, a textconv driver, a -diff attribute and diff.interHunkContext from changing the hunks, and it scans the working tree, which holds the staged text of each staged .jl file, since a partly staged one is refused before. The diff runs without the variables GIT_DIFF_OPTS, GIT_ICASE_PATHSPECS and GIT_GLOB_PATHSPECS. A hit of severity warning or hint never blocks: after the hits of severity error, the stage prints ast-grep: <n> hit(s) of severity warning or hint — advisory and one line per hit. A hit of severity info, such as one of parse-error, is not printed. The stage prints ast-grep: clean when no hit has severity error, warning or hint. To silence one hit, write # ast-grep-ignore: <rule-id> at the end of its line or on the line above. Without ast-grep on the PATH, with an ast-grep that cannot start, without an sgconfig.yml, with a configuration that applies no rule to the staged files, on an exit code other than 0 and 1, on an output that is not one JSON object per line, without a JSON package that loads, or when the limit runs out, the stage prints one line that starts ast-grep: skipped — and names the reason, and the commit passes. ast-grep and its parser are installed on each machine, and a machine without them must still commit. The stage reads the JSON output with JSON from the harness's Julia environment.

pre-commit-test.jl runs both hooks, unchanged, in fixture package repositories (julia --startup-file=no pre-commit-test.jl). For pre-commit: a formatted file, also under a non-ASCII name, passes, and a misformatted file, a renamed misformatted file, a file that does not parse, a file that does not load, a file that is not NFC and a change below test/ without test-layout.jl or out of its layout are refused, and so is a JuliaFormatter older than 2.14; a file that does not parse beside a formatted one is listed alone; a staged symlink to a missing file or to a directory is refused with one line; a Project.toml with an indented, single-quoted name runs the load test, one with a name and no uuid runs none and says so, one without a name says nothing of it, one that does not parse is refused with the error's location, and so is one whose name is not an identifier, without running the code that the name holds, or is the keyword end; a file that does not parse is listed with the error's location and the parser's reason; a failed load report starts at its ERROR: line; a commit that only deletes a .jl file runs the load test; without julia, or with a julia that cannot start, a commit with no .jl file and no test/ path passes; without julia, any other commit, a .jl file that became a symlink too, is refused; a missing fatou, a fatou that cannot start, a fatou that fails, and the findings of fatou, give their lines, and the staged paths reach fatou after --; a commit of one .jl file starts julia from the PATH once; an interrupted commit stops its load test; a partly staged .jl file is refused with its name, also under GIT_GLOB_PATHSPECS, and a fully staged one passes, also beside an unstaged edit of another file or of a path that its name, read as a glob, matches. For the ast-grep stage, a hit on a line that a commit adds, also on the last line of a hunk or inside a hit that spans lines, is refused with its line; a hit on lines that a commit does not add, also after a rename or a deletion, warns; the added lines do not change with an external diff program, a textconv driver, a -diff attribute, diff.interHunkContext, GIT_DIFF_OPTS, GIT_ICASE_PATHSPECS, GIT_GLOB_PATHSPECS or glob characters in a path; a hit of severity warning or hint warns on an added line; a parse-error hit and a silenced hit are not printed; an interrupt while JSON loads is no skip; and each case of a skip gives its one line. Each fixture of the stage holds an sgconfig.yml that names the rules of the tree under test and the parser by absolute path: ast-grep/julia.dylib of the tree where it exists, as in CI, else the one of the research tree's Harness/. It checks the time limits of the lint stage and the load test, also for a child that holds the output and for a process that leaves the group, that the time box sends no SIGKILL after it returns, and that pre-commit.jl and pre-push.jl are in SciML style. For pre-push it checks each case of the gate and the suite, the interrupt with a group that outlives its SIGKILL, and the headline of an error. CI runs it on Linux.

pre-push and pre-push.jl ​

pre-push is the shared pre-push hook of the Julia repositories. Like pre-commit, it is a bash launcher that starts pre-push.jl beside it, and passes it git's ref lines on stdin. A push that updates no main or master passes without starting julia. Without julia on the PATH, a push of either is refused with pre-push: julia is not on the PATH. The program runs the full test suite, but only on a push to main or master. A push to another branch passes at once, and CI tests it.

For a package, the hook runs Pkg.test("<package>") with --check-bounds=auto, and passes the flag to the test process through julia_args: up to Julia 1.12, Pkg.test gives the test process --check-bounds=yes whatever the calling process uses. A repository has a package when its Project.toml, read as TOML, has a name and a uuid. For a repository with no package, it runs test/runtests.jl in the root environment, which ignores test/Project.toml (K134). With neither, it runs nothing and passes. A Project.toml that does not parse refuses the push with one line that holds the first two lines of the error, the message and its location. A package name that Base.isidentifier refuses, or that the parser of the running Julia does not read as that one name, such as a keyword, refuses the push with one line before any suite starts. A failure of the suite refuses the push with ERROR — tests must pass before pushing to main or master. The suite runs in the working tree, not on the pushed commit (K133).

The suite takes 10 to 30 minutes and prints nothing until it ends. That is not a hang. The suite runs in a process group of its own. When you interrupt the hook with Ctrl-C or SIGINT, it sends the interrupt to that group, waits until no process of the group is left, and exits with status 130. When a process of the group still runs 30 s after the interrupt, also after the suite itself has ended, the hook sends SIGKILL to the group. When the group still answers 10 s after the SIGKILL, such as for a process that SIGKILL cannot end, the hook stops the wait, prints one line that names the group ID and says that processes of the suite are left, and exits with status 130. A second interrupt does not end the wait. harness repos push runs this hook in each repository.

pre-commit-wiki ​

pre-commit-wiki is the pre-commit hook of the four prose repositories: Knowledge, Environment, Tasks and Library. harness wiki-lint-hook --apply installs it into each as .githooks/pre-commit, and sets core.hooksPath.

The hook is a Python script that imports only the standard library, in the closed set of Python 3.0 forms of bin/harness, so an old python3 prints the version refusal of bin/harness instead of a syntax error. It runs harness wiki-lint --quiet with bin/harness of $RESEARCH_ROOT/Harness, or of ~/Research/Harness if RESEARCH_ROOT is not set, over all four trees. An ERROR in any tree blocks the commit, even an ERROR in another repository: the trees link to each other, so an edit here can break a link there. A warning does not block. A missing bin/harness blocks too. The lint takes about a second.

In a repository whose staged pyproject.toml holds a [tool.ruff] table, the hook also runs ruff format --check, ruff check and basedpyright on the staged Python files and the tools' configuration, which it writes into a temporary directory. The tools come from the bin/ of the harness's Python environment; where the environment lacks one, the hook refuses the commit with one line that names harness install --apply. Every check runs, and the hook refuses the commit when one fails. No Julia repository uses this hook; it uses pre-commit.

nfc.jl ​

nfc.jl reports or applies Unicode NFC normalisation. In NFC, a letter such as ẋ is one code point, not a base letter and a combining mark. Julia reads both forms as the same name, but a byte search for one form does not find the other.

bash
julia --startup-file=no nfc.jl                     # check every tracked source file here
julia --startup-file=no nfc.jl --apply             # rewrite them
julia --startup-file=no nfc.jl a.jl b.md           # check just these paths
julia --startup-file=no nfc.jl --apply src/x.jl    # rewrite just this one

With no path, it checks every tracked file of the repository in the current directory that is valid UTF-8. The exit status is 0 when each checked file is NFC, and 1 when one is not or when a named file is not valid UTF-8. With --apply, the exit status is 0 after the rewrite.

Normalisation can change a string literal. Before --apply, check what reads such a literal, for example a doctest. The pre-commit hook has its own copy of the check, in pre-commit.jl, and names this script for the fix. The rule generated-hooks-and-workflows and the agent julia-pr-shepherd tell an agent to run it.

explicit-imports.jl ​

explicit-imports.jl runs ExplicitImports.jl on a package and prints what it finds. It loads the package, so it sees the real bindings. fatou lint cannot do this, because its unused-import rule does not follow include.

bash
julia --project=<pkg> explicit-imports.jl <PkgName>

It prints the implicit imports, the names that a using brings in without a name list. Then it runs four checks and prints ok or FAIL for each: stale explicit imports, explicit imports through their owner, self-qualified access, and qualified access through the owner. It changes no file. Run it on Julia 1.11 or later, because the ownership checks are reliable only on that version. No hook, skill or agent calls it.

format-tree.jl ​

format-tree.jl runs JuliaFormatter over every tracked .jl file of the repositories below Packages/ and Experiments/.

bash
julia format-tree.jl            # report only, changes nothing
julia format-tree.jl --apply    # rewrite files in place

It formats each repository with its own .JuliaFormatter.toml, and skips a repository with no such file. It skips the directories prototyping/, legacy/ and obsolete/. It works on one file at a time, and writes the name of each file to a marker file before it starts.

harness format runs this script. When JuliaFormatter crashes the process on a file, harness format moves that file to a skip list and runs the script again, until it ends cleanly. Use harness format, not the script, for a run over the tree. For the files of one change, run JuliaFormatter on those files only.

release-notes.jl and release-notes-test.jl ​

release-notes.jl builds the body of the @JuliaRegistrator comment from the CHANGELOG.md of a package. It refuses a breaking release whose notes have no breaking-changes section, because the registry then blocks the release.

bash
julia --startup-file=no release-notes.jl [package-dir] > notes.json
gh api repos/<owner>/<repo>/commits/<SHA>/comments --input notes.json

The version comes from Project.toml. The notes are the CHANGELOG.md section of that version. The JSON goes to stdout. On a failure, the script writes the reason to stderr, nothing to stdout, and exits 1. It fails when the section is missing or empty, or when a breaking release has no heading that contains "breaking". The first version of a package is never breaking. The skill julia-release runs it.

release-notes-test.jl checks the script on fixtures, among them the two cases that must fail with an empty stdout.

bash
julia --startup-file=no release-notes-test.jl

workflows/CI.yml ​

workflows/CI.yml is the CI workflow. harness workflows copies it to .github/workflows/CI.yml of each repository. It runs on a push to main or master, on a tag, on a pull request and by hand. It reads the package name from Project.toml at run time, so one file fits every repository.

jobwhat it runs
groupsreads test/ci-groups.toml and gives the list of test groups to the two jobs below; one empty group where the file does not exist
testthe tests on Julia min and 1, on Ubuntu, macOS and Windows, once per test group; pre and nightly on Ubuntu, the whole suite, as information only
downgradethe tests with each direct dependency of Project.toml and test/Project.toml at the lower bound of its [compat] entry, the two resolved together, on Julia min, once per test group; information only
doctestdoctest of the package on Julia 1 on Ubuntu, where docs/Project.toml exists

The matrix names Julia versions by alias, min and 1, so the names of the checks stay the same in every repository without test groups. Branch protection needs those fixed names. Only the entry of Julia 1 on Ubuntu measures coverage and sends it to Codecov, once per test group. A repository that needs another job gets its own extra workflow file, not an edit of this one. No checkout keeps the token, because the build and the tests run code of the package and its dependencies.

Test groups ​

A repository whose suite is too long for one job lists its test groups in test/ci-groups.toml. The file is in the repository, so CI.yml stays identical in every repository:

toml
# The test groups that CI runs as separate jobs.
groups = ["core", "slow", "properties", "long"]

The test and downgrade jobs then run once per group, with the group as the argument of Pkg.test, and each job name ends with - <group>, such as Julia min - ubuntu-latest - default - long. Without the file, the jobs run the whole suite, and the job names do not change. Each group of Julia 1 on Ubuntu sends its own part of the coverage; Codecov merges the parts of one commit. pre and nightly run the whole suite in one job either way.

The file lists core, slow and the repository's own groups, and GROUPS in runtests.jl runs exactly these groups for empty ARGS, so Pkg.test() and the pre-push hook still run every group. The rule julia-tests, scripts/test-layout.jl and verify-workflows.jl check this. harness ci-protection reads the file and requires one check per group and version and system.

Each job runs its group alone, so a device group such as metal does not run in the required macOS jobs, where empty ARGS runs it without a group file. The file names the repository's own device workflow instead, and harness ci-protection requires every job of that workflow that is not a warning:

toml
groups = ["core", "backends", "optimizers", "slow"]
workflows = ["Metal.yml"]

run-tests.jl <repository> affected selects from every group of the file except slow, so a file that a repository moves out of core keeps its quick check.

A pull request that adds or changes the file reports the new check names, but the ruleset still requires the old ones. Merge that pull request with the admin bypass, and then run harness ci-protection --apply.

workflows/Dependents.yml ​

workflows/Dependents.yml tests the direct dependents of a base package against the head of a pull request on the base. It runs the core test group of each dependent. harness workflows copies it to .github/workflows/Dependents.yml of each base that the profile key dependents_bases names. It deletes the file from every other repository. The workflow runs on a pull request that changes src/, ext/ or Project.toml, and by hand. A push to main does not run it. One concurrency group per ref cancels a run that a newer push replaces. The workflow can only read the repository. No checkout keeps the token, because the tests of the dependents run code of other repositories.

jobwhat it runs
listreads the dependents from .github/dependents.toml with dependents.jl list; it fails with a line that names harness dependents --apply when the file is missing
testone job per dependent, on Ubuntu with Julia 1, 60 minutes at most, and fail-fast off: the compat check; a setup step, Pkg.develop of the head into the dependent's project, and a test step, Pkg.test(test_args = ["core"]), which runs only after its setup succeeds; on a failure of either, the same two steps against the default branch of the base, in a second checkout of the dependent, so that the resolution of the run against the head does not carry over; then the row of the dependent

The row is one of five:

  • excluded: the dependent's [compat] entry excludes the head, for example after a breaking bump. The job does not test it, because a test needs a compat override that no user can install.
  • green: the setup and the tests against the head pass.
  • regression: the setup against the head fails, and the setup against the default branch passes. Or the tests fail against the head and pass against the default branch. A failed setup against the head counts as a regression. The compat check has already left out a head that the dependent's [compat] excludes. So the job reads the failure as a head that the resolver cannot install beside the other dependencies of the dependent. The log of the head's setup step names the cause, such as a conflict ("empty intersection …").
  • known red: the tests fail against both. The pull request does not cause it.
  • inconclusive: the setup or the tests fail against the head. The setup against the default branch fails too, for example on the registry or a download. The row names which setup failed: the default branch's alone, or the head's and the default branch's. A setup or a test step that GitHub cancels, for example at the timeout of the job, also makes the row inconclusive. The row then names the cancelled step.

A regression and an inconclusive row fail the job. An inconclusive row asks a person to read the log or to run the job again. A step that fails before the row also fails the job. Two examples are the compat check and the checkout of a dependent that the token of the base cannot read. The workflow is advisory: harness ci-protection does not require it.

workflows/dependents.jl ​

workflows/dependents.jl holds the logic of the jobs of Dependents.yml. It is a script, so the tests of the harness can run it. harness workflows copies it to .github/dependents.jl beside the workflow.

bash
julia --startup-file=no dependents.jl list <dependents.toml>
julia --startup-file=no dependents.jl excluded <base> <dependent>
julia --startup-file=no dependents.jl row <name> <excluded> <head setup> <head test> <main setup> <main test>

list prints the dependents as a JSON array, the matrix of the test job. excluded reads the version of the base's Project.toml and the dependent's [compat] entry for the base. It reads the entry with Pkg.Versions.semver_spec. It prints excluded=true when the version is outside the entry. It prints excluded=false when the version is inside, or when the dependent has no entry. row prints the row from the outcomes of the four setup and test steps. A step that did not run has the outcome skipped or an empty one. row appends the row under a header to the job summary, and exits with status 1 for a regression and for an inconclusive row. Where the variable is set, each command writes its result to $GITHUB_OUTPUT or $GITHUB_STEP_SUMMARY.

These inputs exit with status 2 and one line on stderr:

  • a missing file, or a file that is not TOML;
  • a malformed entry, or a base version that is no version number;
  • a [compat] entry that is no version specifier;
  • a combination of outcomes that is none of the five rows.

workflows/Documenter.yml ​

workflows/Documenter.yml is the documentation workflow. It builds the documentation with docs/make.jl and deploys it. harness workflows copies it to .github/workflows/Documenter.yml of each repository that has a tracked docs/make.jl.

It does not go into a repository that the profile key docs_exceptions or docs_additions names. Such a repository keeps its own file: its documentation is a pipeline of several jobs, or it needs an extra step. The doctests do not run here; the doctest job of CI.yml runs them. It runs on the same events as CI.yml, on Ubuntu with Julia 1. The checkout does not keep the token: the deploy pushes from a new repository of its own, with DOCUMENTER_KEY or GITHUB_TOKEN. A private repository names devbranch in its deploydocs call: without it, Documenter reads the default branch with git remote show origin, which needs the token there, and falls back to master.

workflows/TagBot.yml ​

workflows/TagBot.yml runs the action JuliaRegistries/TagBot for a registered package. harness workflows copies it to .github/workflows/TagBot.yml of each package below Packages/, and not into an experiment.

It runs on a comment that the registry posts as JuliaTagBot, and by hand, with the input lookback. An if: condition stops it on every other issue comment.

workflows/codecov.yml ​

workflows/codecov.yml is the Codecov configuration. harness workflows copies it to codecov.yml at the root of each repository.

It sets a threshold of 1 % on both the project status and the patch status. Without the threshold, Codecov fails a pull request for any decrease of the coverage. With it, a real regression still fails, but a small drift does not. The coverage comes from one entry of the matrix of CI.yml, or from that entry of each test group, which Codecov merges.

workflows/dependabot.yml ​

workflows/dependabot.yml is the Dependabot configuration. harness workflows copies it to .github/dependabot.yml of each repository.

Each week, Dependabot proposes to raise the [compat] bounds of the root Project.toml. It does not update test/Project.toml, docs/Project.toml or the GitHub actions. Change the version of an action in the templates, so that the copies stay identical. The configuration ignores the standard libraries, whose bound stays at "1".

verify-workflows.jl ​

verify-workflows.jl checks that the workflows of every repository below Packages/ and Experiments/ match the templates.

bash
julia verify-workflows.jl            # report
julia verify-workflows.jl --quiet    # only deviations and the summary

It checks these points:

  1. CI.yml, dependabot.yml, TagBot.yml and codecov.yml are byte-identical to the templates, in the working tree. TagBot.yml must be absent in an experiment. Dependents.yml and dependents.jl are byte-identical in each base of dependents_bases, which also has .github/dependents.toml, and absent from every other repository. The content of dependents.toml is the check of harness dependents.
  2. The same files on the default branch, for a repository that is on another branch.
  3. The job names of CI.yml are the names of the required checks.
  4. No Register.yml, Documentation.yml, CompatHelper.yml or other forbidden file exists.
  5. Each uses: names the expected major version of its action.
  6. A test/ci-groups.toml lists distinct group names, each group has an if in test/runtests.jl, and GROUPS runs exactly these groups for empty ARGS. Each workflow of its workflows is a file in .github/workflows/ and is not an installed one.

It prints the required checks of each repository that has a test/ci-groups.toml. It also checks that a repository of docs_additions keeps the body of Documenter.yml. It reports the repositories whose doctest job skips itself. It exits with status 1 when a repository deviates. It reads the profile for docs_exceptions, docs_additions and dependents_bases. It reads a key that the profile does not have as an empty list, so without dependents_bases no repository is a base.

Run it after harness workflows --apply, and before a change to CI. harness ci-protection --apply refuses to run when it fails. The rule generated-hooks-and-workflows and the agent ci-triage name it.
