Tests and CI ​

A test runs the code and compares what it does with what it must do. An agent writes tests easily, and runs them often, so the questions are which tests run when, how long the agent waits for them, and which result counts. This page describes the test layout of a Julia package, the three tiers of a test run, and the checks between an edit and a merge.

The test layout ​

Each test file of a Julia package belongs to one group, and test/runtests.jl runs the groups that its arguments name:

groupholdsruns
corethe fast tests: each file runs in at most 60 s, coldby default, and in every affected run
slowthe tests that take longerby default
docteststest/quality/doctests.jl onlywhen named
metal, cudathe tests of a device backendmetal by default on Apple silicon, where the package has it; otherwise when named
brokena file that cannot load, with its issuewhen named

Aqua and, where the package has a hot path, JET run as quality tests in test/quality/. The rule julia-tests states the layout, and test-layout.jl checks it on every commit that touches test/. A fixed layout lets a script, not the agent, decide which tests a change reaches.

The three tiers of a test run ​

An agent checks its work many times during a change. A cold Julia process pays for the start, the package load and the compilation each time, so the harness gives three tiers, cheapest first (julia-code):

  1. A warm session. A Kaimon session reloads src/ before every evaluation, so an edit is checkable in seconds. This is the default while the agent works.
  2. The affected tests. run-tests.jl <package> affected runs the core files that the diff against origin/main can reach, and the quality files, in one fresh process. With a test/ci-groups.toml, it selects from every group of that file but slow. A changed Project.toml runs the full suite.
  3. The full suite. Pkg.test(), before a push. It takes seconds in a small package and up to 100 minutes in CI in the large ones.

A measurement of time or allocations is the exception: it needs a cold process, never the warm session.

run-tests.jl exits 0 on a pass, 1 on a failure, 2 on bad arguments or a layout outside the convention, and 3 on a failure of the script. Its mode select prints what affected would run, and runs nothing. The log goes to a file, so the agent reads a short verdict and not the whole output.

Waiting for a long run ​

A full suite of a large package runs for many minutes and prints nothing. An agent that waits for it in its own context keeps that context alive at full cost. So the long runs go to julia-test-runner, on a medium model, which returns one verdict per testset and the failing output verbatim. In the builder-critic loop it runs beside each critic, so the suite and the critic finish at about the same time. A builder runs every command under five minutes itself, and leaves the longer runs to its caller.

From an edit to a merge ​

The checks between an edit and a merge. An edit meets three groups of checks before you merge it: the pre-commit hook on every commit, the checks of the builder-critic loop, and CI on every push to the pull request.

  1. The pre-commit hook, on every commit: the test layout, JuliaFormatter, Unicode NFC, and whether the package loads in a fresh process. fatou lint runs too, as advice only. The hook is the same in every package, and harness githooks --apply installs it (pre-commit).
  2. The builder-critic loop: in each round the builder runs run-tests.jl affected and the named mutants, the round-1 critics run the named mutants again, and julia-test-runner runs the full suite beside the critic. Before the pull request, the verifier runs the dispatch delta. For a part with a spec-delta spec, each round also runs the spec's checks on the head and pushes the branch for CI. gate.jl runs these checks of a Julia package as one command, when you or an agent call it.
  3. CI, on every push to an open pull request, and on a push to main or master: the workflow CI.yml below.

The shared pre-push hook runs Pkg.test on a push to main or master only; a push of another branch passes at once, and CI tests it once its pull request is open. Known issue (K133): the hook tests the working tree, not the commit that it pushes.

The CI of a package ​

The CI workflows of a package come from the harness, and are byte-identical in every package. harness workflows --apply copies them, and verify-workflows.jl checks that every copy matches its template:

job or filewhat it runsrequired
groupsreads the test groups of test/ci-groups.toml, where the file existsno
testthe tests on Julia min and 1, on Ubuntu, macOS and Windows, once per test group; pre and nightly on Ubuntuyes, except pre and nightly
downgradethe tests with each direct dependency at the lower bound of its [compat] entry, once per test groupno: information only
doctestthe doctests of the docstrings and of the manual, where docs/Project.toml existsyes
Documenter.ymlthe documentation build and its deployno
TagBot.yml, codecov.yml, dependabot.ymlthe tag of a registered release, the coverage threshold, the weekly [compat] proposalsno

The matrix names Julia by the aliases min and 1, so the names of the checks are the same in every repository without test groups. A suite too long for one job lists its groups in test/ci-groups.toml, and each test check then ends with - <group>; see test groups. harness ci-protection sets a ruleset on the default branch with those names as required checks, and refuses to run while verify-workflows.jl fails. A red required check stops the merge; the ci-triage agent separates a real failure from a known one.

The harness's own tests ​

The harness is Python and has its own suite. harness test runs the selftest of each module in a process of its own, the hook probe and the verb sweep. Its CI has three workflows:

workflowjobs
test.ymlpython, empty-home, changelog, systemd, dotfiles, lint, leaks, strict
julia.ymltest, the tests of the Julia scripts, and ast-grep, the tests of the syntax rules
docs.ymldocs, the build and the checks of this site

Development describes each job.

Planned ​

  • A regression set for the critics (work in progress): known defects, planted in branches, to measure whether a change of a critic's prompt finds more or fewer of them.
  • Tests of the dependents (planned): a change of a base package runs the tests of the packages that depend on it, before its release.
  • Property-based tests (planned): generators for the inputs of a numerical method, so that a test covers a class of inputs and not only the cases that its author chose.

In another language. The tiers and the order of the checks work in any language. The harness's Python uses harness test as its gate, and ruff and basedpyright as its static checks; the builder-critic loop names the agents for each language.
