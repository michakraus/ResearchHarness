- **git, gh and glab use one fine-grained forge token per owner, from a token store that `harness install` routes.** The store `~/.config/research-harness/forge/<host>/<name>.store` holds one token per GitHub owner, `default.store` for every other owner, and one GitLab group token, each as a `credential-store` line, mode 600. Where the store exists, `harness install` renders `~/.config/research-harness/forge.gitconfig`, mode 600, with git's owner-scoped credential sections and a get-only helper, so a `git credential reject` never erases a token, and a reset for `gist.github.com`; it exits 2 on a store file that the group or others can read, a file name that is no owner's name, or a line of another host, and prints a notice while `~/.gitconfig` does not include the file. The new `~/.local/bin/gh`, installed with the launcher from `scripts/gh-token.py`, runs gh with the token of the owner that `-R`, `GH_REPO`, the `gh api` endpoint or `origin` names, and with no token and an empty `GH_CONFIG_DIR` otherwise. `agentbox` exports `GIT_TERMINAL_PROMPT=0`, a fresh empty `GLAB_CONFIG_DIR`, and `GITLAB_HOST` and `GITLAB_TOKEN` from the store's one GitLab file. The settings template denies the store to Claude Code's sandbox, and every frontend's `own` lets its srt file read it. The tokens themselves, and the removal of the broad logins, are steps of the user that `docs/src/components/sandbox.md` lists.
